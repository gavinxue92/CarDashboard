# 海外汽车服务工作台 · 设计说明（v4）

> 本文件只记**布局与已实现范围的现状**，配套可点击原型：`design/prototype.html`（单文件，无依赖，双击即可在浏览器打开）。
> **v4 的驱动文档是 `design/SHELL-ROUTE.md`**（载体改为 Electron 套壳官方网页版）；v3 的驱动文档是
> `design/CONVERSATION-MODE.md`（客户对话模式，含八个重做理由与逐项决策）。本文与两者不矛盾；凡被后续变更推翻处，本文就地标注。
> 设计目标不是把功能画全，而是**把"继续加功能的接口"设计出来**——后续一个功能一个功能往里填。

## 一、v2 要解决旧版的什么问题

旧版把 18 项功能平铺在左侧导航里，未做的也占位可点，点进去是空的。这不是预留入口，是提前欠债：
用户分不清"哪些能用"，也会把空页面误读成"坏了"。

v2 的取舍只有一条主线：**把"承诺"和"占位"区分开**。

| # | 改动 | 状态 | 解决的问题 |
|---|---|---|---|
| 1 | 导航瘦身 + 灰色「预留（未开放）」区 | 已采纳 | 未做的功能不再伪装成可用入口；灰度本身即诚实 |
| 2 | 账号切换升为顶部全局切换器 | **未采纳** | 保留在左侧导航（按用户决定） |
| 3 | 右栏从「聊天面板」升级为「客户工作区」 | 已采纳 | 对话 / 客户档案 / 成本精算 同屏，不用跳页 |
| 4 | 会话列表项升级 | 已采纳 | 手机号改为「客户名/公司 + 国家 + 意向阶段 + 待跟进时长」 |

> 关于 2：账号的作用域确实是全局的（切换后会话、客户、业务数据全变），放导航里语义偏弱。
> 本次按用户决定保留原位置；若将来账号数变多（矩阵化管理），这一处建议重新评估。

### v3 相对 v2 的变更（原型已改，详见 `CONVERSATION-MODE.md`）

| # | 改动 | 为什么 |
|---|---|---|
| 1 | 消息模型把**方向与语言解耦**（`body{text,lang}` + `translation{text,lang,state}`），主气泡按语言选边 | v2 用 `dir` 猜哪边是原文、硬编码 `zh`/`en` 两字段，违反既定原则「语言对是数据不是代码」 |
| 2 | 补**发送状态**（sending/sent/delivered/read/failed）与**翻译状态**（none/pending/done/failed/skipped） | 后端已是异步翻译 + 先落库原文，UI 必须容得下"翻译中/失败/跳过" |
| 3 | `origin='phone'` 在气泡上显示「手机端 · 未经翻译」 | 手机手打绕过翻译层是已知缺口，必须**显性化**而非无声吞掉 |
| 4 | 消息**逐条操作条**（复制 / 重译 / 引用 / 转发到右栏 / 收藏为话术 / 撤回） | v2 消息节点没有任何操作位 |
| 5 | **发送前常驻译文预览**（译文可就地改、就绪前禁用发送、术语命中可点） | 后端已强制 `draft()`/`send()` 两步，v2 却是静默直发 —— UI 落后于契约 |
| 6 | 右栏改**常驻 + 可展开覆盖层**，与输入区**不再互斥** | v2 切到「客户档案」会把输入区 `display:none`，"看档案就不能发消息"业务上不成立 |
| 7 | 「**24 小时窗口**」三处（筛选 chip / 列表徽章 / 标题行）全部换成「**待跟进**」 | 窗口是**官方 Cloud API 的约束**；走非官方路线后无此限制，该徽章成了误导信息 |
| 8 | 会话列表顶部加**账号筛选器**（含每号连接状态点） | 会话数据早有 `account`，界面完全没有账号维度，无法按号排查"哪个号掉线" |
| 9 | 「**群组**」筛选恢复，并按**会话类型**处理（群头 + 成员数） | v2 移除群组的理由是官方 API 收不到群组；非官方路线下该理由已失效 |
| 10 | 常驻 chip 收敛为 **未读 / 待跟进 / 群组**，其余（阶段/国家/标签）收进「筛选 ▾」 | 不平铺 7 个 chip；同"导航瘦身"原则 |

### v4 相对 v3 的变更（原型同步改造，详见 `SHELL-ROUTE.md`）

| # | 改动 | 为什么 |
|---|---|---|
| 1 | **对话区归属变更**：中间由「自绘对话区」改为「官方网页版 `<webview>` 占满」 | 用户决定走**套壳**（原话「我需要套壳，套壳后再进行扩展」）。媒体 / 回执 / 撤回 / 群组 / 历史随之全部免费 |
| 2 | v3 的消息模型 / 悬浮操作条 / 双语副行**目标不变，实现方式改为注入** | 对话区不再是我们的 DOM；改用 preload 观察 + 打标 + 插副行 |
| 3 | **「发送前常驻预览」被推翻** → 改为「拦截发送动作 → 出覆盖层」 | 输入框属于官方网页版，无法在其下方常驻任何东西（`SHELL-ROUTE.md` §2.3） |
| 4 | **一期只做观测同步**，翻译与注入落二期 | 用户决定。一期交付的是"工作台聚合"（多号同屏 + 会话列表 + 客户档案 + 待跟进），翻译二期补 |
| 5 | 快捷插入栏**位置与归属不变**，但插入动作改为「写进网页版输入框成为草稿」 | 它在外圈、仍是我们自己的 DOM，是**原创资产**；纪律「插入 ≠ 发送」不变 |
| 6 | 会话列表 / 右栏 / 导航**不受影响** | 三者都在外圈，数据来自我们自己的库，不依赖对方 DOM |

## 二、布局结构

四栏（v3 起），从左到右作用域由大到小；**对话区永远在左，右栏常驻**。
**v4 起，中间那栏是官方的页面，不是我们画的**：

```
┌────────┬──────────────┬────────────────────────┬──────────────┐
│ 导航    │ 会话列表      │ 对话区 = 官方网页版       │ 右常驻栏      │
│ 200px  │ 272px        │ <webview>（别人的页面）  │ 320px        │
│        │              │                        │              │
│ 沟通    │ 搜索          │ 客户名·国家·阶段          │ 客户档案      │
│ 客户会话 │ 账号筛选器    │ 待跟进 3h   ●销售A号已连接 │ 成本精算      │
│ 业务    │ 未读 待跟进 群组│ ─────────────────────── │ （可展开为    │
│ （预留）│ 筛选 ▾        │ WhatsApp 原生（免费）：    │   覆盖层）    │
│ 账号    │              │  媒体·回执·撤回·群组·历史  │              │
│ （预留）│ 会话项        │ 注入（圈一 preload）：     │              │
│ 预留区  │  · 客户名     │  · 译文副行        【二期】│              │
│        │  · 国家·阶段  │  · 手机端未翻译标记       │              │
│        │  · 待跟进徽章 │  · 出站确认层(覆盖)【二期】│              │
│        │  · 消息摘要   │ ─────────────────────── │              │
│        │              │ 快捷插入栏（外圈，我们的）  │              │
└────────┴──────────────┴────────────────────────┴──────────────┘
```

**保住的旧版资产**：底部的**快捷插入栏**。它是"工作台"区别于"聊天软件"的分水岭——
业务模块的产物可以直接变成聊天里可插入的内容。它位于**对话框之外（外圈）**，因此**不受套壳影响**，
仍是我们的 DOM 与原创资产。纪律照旧：**插入 ≠ 发送**（先进网页版输入框成为草稿，再走译文确认）。

> 与第三方客户端（拓译翻译）的对照见 `REF-TUOYI.md`：它的对话区是别人的网页，只能用叠加/弹窗。
> **我们已改为套壳，对话区也变成"别人的网页"**——但**右栏在对话区之外（外圈）**，仍应常驻，不照抄弹窗。
> 变化只发生在**对话区内部**：那里的东西（消息操作条、发送前确认）不能常驻，只能走注入或覆盖层。

## 三、本次完整实现的功能：客户会话（底座）

这是第一个做完的功能，因为它产出后面所有模块要用的数据。

> ⚠️ **2026-10-13 起，本节「对话区」相关条目已降级为"待按套壳方式实现"**（见 §一 v4 变更表）。
> 它们在原型里仍可交互，但**实现路径变了**：消息渲染、悬浮操作条、双语副行改走**注入（圈一）**；
> 「发送前常驻预览」**被推翻**，改为「拦截发送 + 覆盖层」。**会话列表、右栏、导航三块不受影响。**

**已实现（原型可交互）**

- 会话列表：客户名/公司 + 国家·意向阶段 + **待跟进徽章** + 未读计数 + 消息摘要（群聊带「群组 · N人」标记）
- 账号筛选器：全部 / 销售 A 号 / B 号 / C 号，每号带连接状态点（已连接 / 需重新扫码 / 连接断开）
- 筛选：常驻 **未读 / 待跟进 / 群组** 三个 chip ＋「筛选 ▾」（意向阶段 / 国家 / 标签）
- 对话区：**主气泡按我方阅读语言选边，副行是对方语言那一侧**（不再用方向猜原文）；顶部「对照」开关可一次性展开全部双语
- 消息状态：出站有 发送中 / 已发送 / 已送达 / 已读 / 发送失败；入站有 翻译中 / 已译 / 翻译失败（可重试）/ 同语种跳过
- 消息逐条操作：点消息出悬浮操作条（复制 / 重译 / 引用回复 / 转发到右栏 / 收藏为话术；出站另有 撤回）
- `origin='phone'` 的气泡显示「手机端 · 未经翻译」
- 输入区：中文输入 → 下方**常驻译文预览**，译文可就地修改、术语命中给可点标记、**译文就绪前发送按钮为禁用态**
- 快捷插入栏：话术（带分组）**插入的是草稿**，不直发；其余插入位仍为预留
- 群聊会话：顶部显示群名 + 成员数 + 成员列表入口
- 右栏常驻：客户档案 / 成本精算同屏，可「展开」为覆盖层
- 客户档案：客户基础信息 + **四个预留的结构化字段**（目的国 / 车型 / 车龄 / 预算）
- 预留项点击给出明确反馈：「尚未开放，仅为预留入口」，不再是"点了没反应"

**刻意没做**

- 真实翻译模型、真实 WhatsApp 通道接入
- 发送侧的「静默直发」开关：**不提供**，维持强制「先看译文再发」（后端 `draft()`/`send()` 已如此）
- 译文颜色 / 背景可配、多引擎切换与对比、历史消息按需翻译、声音克隆（逐项理由见 `CONVERSATION-MODE.md` §五）
- 通话翻译、WhatsApp 群发、获客相关、PI 合同、样板车展厅、网页版消息/后台

## 四、预留给后续模块的入口

这是 v2 最重要的部分：**今天留的是"数据的形状"和"模块之间的墙"，不是"模块本身"。**

| 入口位置 | 留了什么 | 服务于哪个模块 |
|---|---|---|
| 客户档案 → 结构化字段 | 目的国 / 车型 / 车龄 / 预算 四个字段位（当前显示"待从会话中抽取"） | 业务 · 成本精算 |
| 客户档案 → 客户基础信息 | 公司、国家/城市、意向阶段、所属账号、首次联系、标签 | 业务 · CRM；获客 · 统计 |
| 会话列表 → 客户维度 | 列表按"客户"而非"号码"组织，天然可聚合 | 获客 · 管线与统计 |
| 右栏 → 成本精算页签 | 页签位置已在，内容为占位说明 | 业务 · 成本精算 |
| 底部 → 快捷插入栏 | 四个插入位的布局已定（样板车 / 素材库 / PI 合同 / 地址） | 业务 · 素材库 / PI 合同 |
| 导航 → 预留区 | 获客管线、WhatsApp 群发、PI 合同、通话翻译、WA 账号矩阵 | 全部后续模块 |
| 会话数据模型 | 每条消息**原文与译文都保留且分列**（`body` 与 `translation` 各带 `lang`，永不合并） | 全部（可追溯 + 后续抽取） |
| 会话 / 客户字段 | `customerId`（客户可关联多会话，聚合功能不做）、`accountId`、`type`（direct/group）、`pinned` / `archived` / `unread` | 业务 · CRM；获客 · 统计 |

**留入口的原则**（按"以后改动的成本"排序）：

1. **数据模型**——成本极高，有了数据就要迁移 → **今天必须留**（上面第一、二、七行）
2. **模块间契约 / 对外接口**——成本中 → 只留对外接口
3. **代码结构与界面导航**——成本低，随时可重构 → **不用预留**

⚠️ 反例：**不要提前搭「插件框架 / 模块系统」**。那是最典型的过度设计，抽象要等真的出现第二个实现时再做。

## 五、已知限制

- 翻译、语言识别、发送状态推进均为**演示模拟**（内置词表 + 定时器），真实实现需接大模型与真实通道
- 「待跟进」当前按"对方最后发言且我方未回"计算，原型里是**预置数值**；阈值（示例 4h 标红）是占位，需真实数据后校准
- 数据是内存中的假数据，刷新即重置；未接任何持久化
- 未接真实 WhatsApp 通道，无签名校验、无幂等、无真实收发
- 「撤回（delete for everyone）」在非官方路线下的可行性**待实测**，原型中先留位
- 视觉主题沿用旧版语言（深色导航 + 浅色内容区）；旧版导航里有「白色主题」项，主题切换尚未实现
- **套壳路线的固有限制（2026-10-13 新增，详见 `SHELL-ROUTE.md` §二）**：
  - 注入层依赖对方网页版 DOM，**改版即可能失效**，需长期维护选择器；必须配失效自检与**显性告警**（不能静默失败）
  - DOM 观察会**重复看到**同一条消息（滚动 / 重渲染 / 切会话都会重放）→ **幂等是头号风险**，
    必须在落库层真正用上按 `messageId` 去重
  - 每账号约 400–500MB 内存（对照 Baileys 约 50MB）
  - 业务员在**手机**上手打的消息仍绕过翻译层，套壳不改变这一点，只能把 `origin=phone` 显性化

## 六、下一步怎么继续加

一次只填一格，每格都遵循同一套路：

1. 在原型里把该功能从"预留"提为"可点"，补上真实交互
2. 更新本文件的「已实现 / 刻意没做」两节
3. 提交一个 commit（含验证记录）

建议顺序（依赖是单向的）：

```
套壳一期（S0 壳与登录 → S1 观测同步 → S2 外圈补齐）
  → 套壳二期（S3 翻译与注入 → S4 出站拦截 → S5 失效告警）
  → 素材库 → 成本精算 → 客户档案深化 → 获客
```

**套壳阶段排在素材库之前**，因为它是所有后续功能的载体：不先把壳立起来，
底部的快捷插入栏就没有可插入的对象（"插入到哪里"都不存在）。阶段定义见 `SHELL-ROUTE.md` §六。

素材库排在成本精算之前，是因为它的成本最低，且能立刻让底部快捷插入栏"有东西可插"，
让"工作台"的形态先立住。
