# 客户对话模式 v3 设计（对话交互形态 + 会话组织模式）

> **状态**：待评审。本轮**只出文档**——不改 `prototype.html`，不改后端代码。
> **触发**：参照拓译翻译客户端（`REF-TUOYI.md`）的设计模式重做我们的客户对话模式（用户决策：两层一起重做）。
> **决策已定（2026-10-13）**：§五 翻译开关粒度 = **L1 全部 4 项 + 同语种跳过 + 术语表可视化（共 6 项）**；
> §一 问题 7 的「24 小时窗口」三处信息**全部换成「待跟进」**。开放项：出站「静默直发」开关本轮不定。
> **前提**：接入路线已定走**非官方路线**（`UNOFFICIAL-ROUTE.md`）。这一前提会让 §一 里的两个现存设计直接失效。

## 一、为什么要重做：现状的八个具体问题

v2 原型的对话区是"能跑通的最小形态"，不是"对的形态"。逐条列问题，每条都要能在重做后指认到具体改动。

| # | 问题 | 现状证据 | 后果 |
|---|---|---|---|
| 1 | **方向与语言被耦合死了** | `altLabel(m)` 按 `dir` 推断副行标签；数据是硬编码的 `zh` / `en` 两字段 | 语言对写死在代码里，违反既有原则「语言对是数据不是代码」；第三个语言进来就要改 UI 代码 |
| 2 | **没有发送状态** | `send()` 直接 push 进数组并渲染 | 真实通道必须有 发送中/已送达/已读/失败；现在无法表达"发出去了但没到" |
| 3 | **没有翻译状态** | `translate()` 是同步函数 | 与后端既有设计矛盾：后端是"先落库原文，再异步调翻译，译文后补"。UI 没有"翻译中/翻译失败/跳过"的容身处 |
| 4 | **消息不能逐条操作** | 消息节点只有气泡和副行链接 | 重译、复制、引用回复、收藏为话术都无处安放 |
| 5 | **发送前不确认** | 「发送」直接落库 | 后端已强制 `draft()` / `send()` 两步（绝不把中文原样发给客户），但原型是静默直发——UI 落后于契约 |
| 6 | **`origin=phone` 在界面上不存在** | 数据模型有 `origin` 字段，原型完全没有 | 业务员手机上手打的消息**绕过翻译层**，界面上看不出来 —— 缺口被无声吞掉 |
| 7 | **「24 小时窗口」是失效指标** | 列表徽章 + 筛选 chip「窗口已关」+ 标题行**三处**显示「窗口已关 · 需模板消息触达」 | **24h 窗口是官方 Cloud API 的约束**。走非官方路线后无此限制、可随时主动发——这个徽章现在是**误导信息**，且占掉了最该显示"待跟进紧迫度"的位置。**决策：三处全换成「待跟进」（§五）** |
| 8 | **账号维度完全缺失** | 会话数据有 `account: '销售 A 号'`，界面上没有任何账号切换 | 管几个号的业务员，列表混在一起没有归属感，也无法按号排查"哪个号掉线了" |

> 问题 7 与 8 不是"做得不够好"，是**路线变更后遗留的错误信息**。这两条优先级最高。
> 另：DESIGN.md 记载的「群组 tab 因官方 API 收不到群组而移除」同样随路线变更而失效，见 §四 B。

## 二、参照对象的真实形态

先纠正两处（含对本仓库既有文档的勘误），否则会以错误前提做设计。

### 勘误：拓译**没有**常驻快捷插入栏

`REF-TUOYI.md` §四.3 与 §4 判断里写过"它天生自带工作台 UI，正好对应我们要的快捷插入栏"。**实测不成立**：

- 它的 CSS 类 `.quick-fill-toolbar` 出现在 `.proxy-ip-manager`（代理 IP 管理）与 `.ai-role-manager`（AI 角色管理）这类**设置表单**里，是表单的填充助手，不在对话区。
- 它往会话里插内容的真实手段是**弹窗**：`快捷消息`（带分组、可批量添加）、`常用口头禅`、`推荐回复`（AI、可按角色分组）、`TTS 语音`（文本转语音 + 声音克隆）、图片。

→ 结论：**"常驻快捷插入栏"是我们的原创资产，不是抄来的。** 这条要改，不然会误以为"跟着它做就行"。

### 它的对话页真实布局：两栏半 + 全靠叠加

| 区域 | 实现 | 备注 |
|---|---|---|
| 账号栏 | `.accounts-sidebar`，`var(--accounts-sidebar-width)` 可拖宽、可折叠（`sidebar-resize-handle` / `.active` 折叠态） | 一号一项 |
| 会话列表 | `.aggregated-chat-list`，顶部 `.search-container`，项 `.friend-item`（高 90px，含 `.pin-indicator`） | 「聚合聊天」可把多账号好友合并展示 |
| 对话区 | **官方网页版原样占满剩余空间** + 注入的悬浮条 | 客户信息在它这里是**弹窗**（`customer-verify-card` / `contact-grid`），**没有常驻右栏** |
| 右侧窄栏 | `.chat-bannel-root`，`--chat-bannel-width: 70px` | 充值/公告一类 |

**关键差异**：它的对话区是别人的页面，塞不进常驻面板，所以只能"叠加"。**我们没有这个约束**（自建 UI + 结构化数据），因此常驻右栏是对的，不该照抄弹窗形态。

### 它已做完、我们缺的具体件（设计层面可借鉴）

| 件 | 它的做法 | 对应我们的什么 |
|---|---|---|
| `XZWMessageBar` | 点消息出横向小条，`insert` / `hideTimer` / 「消息栏已插入」「消息栏已移除」「找不到目标元素或其父元素」 | §三 B 消息悬浮操作条 |
| `translationConfirmDialog` | 拦住发送后弹窗确认，文案「翻译结果」「用户取消发送翻译结果」 | §三 C 发送前确认（形态不照抄） |
| `pendingOriginal` | 「保存待匹配原文」——原文/译文异步配对 | §三 A 翻译中/待补状态 |
| `interactionInterceptor` | `beforSend` / `realSend` / `sendConfirm` / `sendConfirmCancel` / `writeTextAndPaste` | 我们在后端已有 `draft()`/`send()`，缺 UI |
| 翻译开关矩阵 | 见 §五 | §五 |
| 会话组织维度 | 会话分类、分组、标签、置顶好友、归档、聚合聊天 | §四 B / C |

## 三、重做之一：对话交互形态

### A. 消息模型：把"方向"和"语言"解耦（问题 1 / 3 / 6 的根治）

现状是"气泡显示中文、副行显示外语"，靠 `dir` 猜哪边是原文。重做后**不再猜**，改成显式字段：

```ts
type DeliveryState = 'sending' | 'sent' | 'delivered' | 'read' | 'failed';
type TranslationState = 'none' | 'pending' | 'done' | 'failed' | 'skipped';

interface ChatMessage {
  id: string;
  chatId: string;
  direction: 'in' | 'out';
  origin: 'system' | 'phone';        // 管道既有字段，UI 必须可见（见下）
  body: { text: string; lang: string };              // 实际传输的那一份
  translation?: { text: string; lang: string;
                  state: TranslationState; engine?: string };
  delivery: DeliveryState;           // 仅出站有意义
  sentAt: string;
}
```

**唯一呈现规则**（不再依赖方向）：

- **主气泡 = 我方阅读语言**（默认中文，来自 `ourLang`）
- **副行 = 对方语言那一侧**
- 副行三态：`查看原文`（收起）→ `原文：xxx`（单条展开）→ `对照`（全局展开，保留现有交互）
- **翻译中**：主气泡显示灰色占位符 + 原文；副行「翻译中…」
- **翻译失败**：主气泡直接显示原文（**消息绝不丢**）+ 副行「翻译失败 · 重试」
- **同语种跳过**：`state='skipped'`，不显示副行（省掉一行噪音）

**`origin='phone'` 必须在气泡上可见**（我们独有的表达，拓译没有）：
手机端手打的消息在气泡角落加一个弱标记，如「手机端 · 未经翻译」。理由：这是已知缺口，界面上必须**显性化**而不是无声——业务员看到标记才知道"这条没走翻译层"，配合既有约定「对外报价/技术类回复走电脑端」。

### B. 消息悬浮操作条（抄 `XZWMessageBar` 的形）

点选消息 → 出横向小条（不用右键菜单，不用悬浮才出现导致误触），动作集：

- 通用：复制 · **重译**（换引擎/重新请求，写回 `translation`）· 引用回复 · 转发到右栏（成本精算/素材库）· 收藏为话术
- 出站额外：查看译文 · 撤回（`delete for everyone`，非官方路线下可行性**待实测**，先留位）
- 自动隐藏（对应它的 `hideTimer`），点空白处收起

**不抄**它的"按类型设 `maxUp` 上限"——那是往别人 UI 里打补丁才需要的防刷屏手段，我们自建 UI 不需要。

### C. 发送前确认：把 `draft()` / `send()` 落成 UI（问题 5）

目标只有一句话：**绝不把中文原样发给海外客户**。拓译用弹窗实现；我们**不用弹窗**（打断节奏），改用输入区常驻预览：

1. 输入中文 → 输入框下方**实时**显示将发送的译文
2. 译文就绪前「发送」按钮为禁用态（文案「翻译中…」）
3. **译文可就地编辑**，编辑后以编辑版为准（翻译不可能 100% 对，必须允许人工兜底）
4. 发送 → 落库原文+译文两份 → 气泡带发送状态
5. **术语命中给可点标记**（如 `国六` → `China VI`）：点开显示术语来源。这是我们垂直领域的差异化，直连既有的 `translation/glossary.ts`（术语表在翻译前后各插一道占位符保护）

### D. 快捷插入栏：从"四个按钮"升级为"业务产物的出口"

保留常驻形态（我们的原创资产），补上内容层与纪律：

| 分组 | 项 | 产出方 | 状态 |
|---|---|---|---|
| 业务产物 | 样板车 / PI 合同 / 成本精算结果 / 地址·联系人名片 | 业务模块 | 预留，待模块上线 |
| 话术 | 常用话术（**带分组**）/ AI 推荐回复 | 沟通模块自有 | 待做（抄它的"快捷消息 + 分组"组织方式） |

**两条纪律**：

1. **插入 ≠ 发送。** 任何插入都先进输入框成为草稿，再走 `draft/send`（即 §三 C 的确认流程）。否则快捷插入会变成绕过译文确认的后门。
2. **承重原则：插入栏的每一项都必须能回答"它是谁产出的"。** 回答不了的说明产出方还没定义 → 保持预留。这就是现有"地址"按钮需要被审视的原因——它的产出方是业务模块还是手工录入，必须定清楚。

**语音**：拓译有 TTS + 声音克隆。我们**不做声音克隆**（合规风险 + 高单值深聊不需要），但"中文文本转成对方语言语音发出"（客户在开车/弱网/不识字场景）**有价值**，列为预留，不进 MVP。

### E. 右栏：常驻 + 可叠加的混合形态（修掉现在的互斥）

现状 `renderWork()` 在切到「客户档案」时把输入区和快捷插入栏 `display:none` —— 意味着**看客户档案就不能发消息**，业务上不成立。

改为：

- 对话区永远在左；客户档案 / 成本精算在**右常驻窄栏**（约 300–340px），**不再互斥**
- 需要看大图（成本精算表格）时，右栏可**展开为覆盖层**（这一步可以抄它的叠加形态）
- 理由：高单值深聊场景，业务员多数时候要"边说边看客户档案"；它之所以只能用弹窗，是因为它的对话区是别人的页面——我们没有这个约束

### F. 状态呈现清单（问题 2 / 3 / 7）

| 层级 | 状态 | 说明 |
|---|---|---|
| 消息（出站） | 发送中 / 已送达 / 已读 / 失败（可重发） | 新增 |
| 消息（入站） | 翻译中 / 已译 / 翻译失败 / 跳过 | 新增 |
| 会话 | **待跟进时长**（对方最后发言距今） | **替代失效的 24h 窗口**（三处全换，已确认），这才是车商真正的紧迫度指标 |
| 账号 | 已连接 / 断开 / 需重新扫码 | 非官方路线下最需要盯的状态，比窗口状态重要得多 |

## 四、重做之二：会话组织模式

### A. 账号维度：筛选器，不是导航项

非官方路线下**一个号 = 一个 linked device 会话**，业务员管几个号必须能按号看。

- 会话列表顶部加**账号切换器**：`全部` / `销售A号` / `销售B号` …，每号带连接状态点（绿/黄/红）
- 默认**聚合所有号**的会话（抄它的「聚合聊天」），可切回单号
- ⚠️ **与既有决定的冲突与调和**：`DESIGN.md` 记载"账号切换保留在左侧导航"（用户此前明确决定，未采纳升为顶部全局切换器）。此处**不推翻该决定**，而是拆成两件事：
  - 「管理账号」= 左侧导航里的「WA 账号矩阵」功能页（保留原决定）
  - 「按号筛选会话」= 会话列表顶部的筛选器（新增，属列表自己的过滤维度）
  
  两者语义不同，不冲突。若用户认为仍是同一件事，则本项降级为"待定"。

### B. 筛选维度：3 个常驻 + 其余收起（问题 7 的替代物）

现有只有 3 个 chip（全部 / 未读 / 窗口已关）。重做后按业务价值排序：

| 优先级 | 维度 | 数据来源 | 备注 |
|---|---|---|---|
| 常驻 chip 1 | 未读 | 已有 | 保留 |
| 常驻 chip 2 | **待跟进** | 对方最后发言 + 我方未回 | **替代"窗口已关"（已确认）**。可设阈值（如对方说话后 >4h 未回） |
| 常驻 chip 3 | **群组** | 会话类型 | **路线变更后恢复**（DESIGN.md 记载的移除理由已失效） |
| 收进「筛选」 | 意向阶段（首询/询价中/已报价/成交/老客户） | 已有 `stage` | |
| 收进「筛选」 | 国家 | 已有 `country` | 非洲各国规则互斥，按国过滤很实际 |
| 收进「筛选」 | 标签（重卡/配件…） | 已有 `tags` | |
| 收进「筛选」 | 归档（已成交/已流失） | 新增 | 本地状态 |

**纪律：不要平铺 7 个 chip。** 常驻只放最高频的 3 个，其余进下拉。这与 v2 的"导航瘦身"是同一条原则。

**群组不是加个 chip 就完事**：群组会话的交互与单聊不同（成员可见、@、群发范围），所以它是**会话类型**，会影响对话区形态——群组会话顶部要显示群名 + 成员数 + 成员列表入口。拓译这块只做了 RPC 能力（`joinGroup` / `addGroupMembers`），UI 层面没做好，我们可以做得更对。

### C. 会话与客户：留字段，不做聚合

现状隐含 1:1（会话 = 客户）。真实情况会有：一个客户多通道 / 一个客户多联系人（采购 + 老板）。

判断：**MVP 不做分离**。拓译也没做（它的好友列表即会话列表），做了就是过度设计。但按既有原则「留数据不留框架」：

- **今天只留 `customerId` 字段**（现在只有 `name`，没有"客户身份"这个概念）
- 会话归属客户；客户可关联多会话 —— **字段留着，聚合功能不做**

### D. 置顶 / 未读 / 归档

- **置顶**：仅本地排序，**不发往通道**（避免污染客户设备；对应它的 `PinnedFriendsService`）
- **未读**：手机端已读的不算未读 —— 靠 linked device 的 read receipt 对齐（非官方路线的天然优势）
- **归档**：纯本地状态，不影响通道

## 五、翻译开关粒度（**决策已定** —— 明细与排除项见 5.3）

拓译的开关矩阵完整清单：

| 开关 | 它的粒度 |
|---|---|
| 发送自动翻译 | 全局 / 分账号 / 分场景（私信、群聊、群组、推文、评论） |
| 接收自动翻译 | 同上 |
| 显示翻译 | 个人显示 / 群聊显示 / 译文**颜色与背景**可配 / 翻译结果样式 |
| 同语种跳过 | 有。原文「与目标语种相同的源文本将直接跳过翻译请求」 |
| 历史翻译 | **按需**（个人历史翻译 / 群组历史翻译），非全量自动 |
| 语言来源 | 我的语言 / 对方语言 / 文本语言 / 录音语种，可分别指定 |
| 翻译渠道 | 微软 / 有道 / 百度 / 腾讯，可切换 |
| 语言习惯 | 「常用口头禅，每行一条」，喂给 AI 推荐回复 |
| 依赖 | `franc`（语言识别，翻译管线入口） |

**场景差异决定该搬多少**（这是判断依据，不是偏好）：

- 它是"一人管几十号、跑量、低单值" → 必须**分场景全自动**，否则人工翻不过来 → 所以它有"发送自动翻译"这个开关
- 我们是"少数几个号、深聊、高单值" → 自动翻译的价值主要在**"收"**；"发"这一侧我们本来就强制"先看译文再发"（`draft/send`）
- → **「发送自动翻译」这个开关对我们没有意义**：我们不应该提供"静默直发"的选项。这条是取舍的核心。

### 递进阶梯 L0–L4（每档逐项列出，便于核对）

**L0 — 全局单一开关**
- 包含项：`translation.enabled`（一个布尔，全场景生效）
- 现状即 L0。问题：群聊里中英混杂时全翻太吵，且无法对群聊单独降噪。

**L1 — 方向 × 会话类型**（共 4 项）

| # | 项 | 默认 |
|---|---|---|
| 1 | `autoTranslateInbound` — 入站自动翻译 · **单聊** | 开 |
| 2 | `autoTranslateInboundGroup` — 入站自动翻译 · **群聊** | **关**（群聊噪音大，改为手动点译） |
| 3 | 出站**固定** `confirm`（先看译文再发），**不提供可关开关** | 强制 |
| 4 | `ourLang` — 我方阅读语言 | `zh-CN`（为将来非中文业务员留位） |

- 不含：同语种跳过、术语可视化、历史按需、多引擎、呈现可配

**L2 — L1 + 同语种跳过**（新增 1 项）
5. `skipSameLanguage`（默认开）。靠语种识别（拓译用 `franc`）；命中则 `translation.state='skipped'`，且**不显示副行**（省一行噪音）
- 依据：拓译原文「与目标语种相同的源文本将直接跳过翻译请求」

**L3 — L2 + 历史消息按需翻译**（新增 1 项）
6. `translateHistoryOnOpen`（默认关）。进会话**不**自动翻历史；点「翻译历史消息」才批量翻，带进度与计数
- 成本：需批量任务 + 进度 UI

**L4 — L3 + 呈现可配 / 多引擎 / 术语可视化**（新增 3 项，逐项判定）

| 新增项 | 判定 |
|---|---|
| 译文颜色 / 背景可配 | **不做** —— 我们主气泡本来就是中文，无需视觉区分，属过度装修 |
| 多引擎切换与对比（微软 / 有道 / 百度 / 腾讯） | **本轮不做**；将来做也藏进设置，不进对话界面 |
| 术语表可视化（命中即可点，看术语来源） | **做** —— 直连 `glossary.ts`，垂直优势 |

### 决策记录（2026-10-13，用户拍板）

**采纳 = L1 全部 4 项 + L2 的 1 项 + L4 的术语可视化 1 项 = 6 项**（逐项可核）：

| # | 项 | 默认 | 落点 |
|---|---|---|---|
| 1 | 入站自动翻译 · 单聊 | 开 | `contact` 扩 prefs |
| 2 | 入站自动翻译 · 群聊（单独） | 关 | 同上 |
| 3 | 出站固定「先看译文再发」，无可关开关 | 强制 | 后端已有 `draft` / `send` |
| 4 | 同语种自动跳过（`skipped` 不显示副行） | 开 | 新增中间件 |
| 5 | 术语命中可点标记（看术语来源） | 开 | 直连 `glossary.ts` |
| 6 | 我方阅读语言 `ourLang` | `zh-CN` | 为将来非中文业务员留位 |

**明确排除（6 项）**：发送静默直发开关 · 译文颜色 / 背景 · 多引擎切换与对比 · 历史消息按需翻译（原 L3）· 推文 / 评论翻译 · 声音克隆。

**开放项（本轮不定）**：出站是否提供「静默直发」开关 —— 用户答复「本轮不定」。
处理：**暂不提供，维持强制 `confirm`**；等真实通道接上后再评估。
留档理由：不应为"静默把中文发给海外客户"提供官方出口，但量产场景是否真需要，要等真实使用数据。

**不搬的三类（原因固定）**：
- 推文 / 评论翻译 —— 我们没有社媒渠道
- 声音克隆 —— 合规风险 + 高单值深聊无必要
- 一号一 IP / 指纹隔离 / 代理池 —— 既有结论：少数几个号自用不需要那套基础设施

## 六、数据结构的最小改动（契约层）

本轮**只写进文档，不改代码**。改动的目标是"以后不用迁移数据"，遵循既有原则「留数据不留框架」。

```ts
// 1) 消息：补两个状态，语言改成数据
//    现状（design 层）：{ dir, zh, en, time }
//    目标：
interface ChatMessage {
  id: string; chatId: string;
  direction: 'in' | 'out';

}

// 2) 客户：语言对从"一个值"扩成"按场景的一组"
interface CustomerPrefs {
  ourLang: 'zh-CN';                // 我方阅读语言
  autoTranslateInbound: boolean;
  autoTranslateInboundGroup: boolean;   // 群聊单独
  skipSameLanguage: boolean;            // 默认 true（L2）

// 3) 会话：补会话类型与本地状态
type SessionType = 'direct' | 'group';
interface ChatSession {
```

## 七、不抄清单（同 `REF-TUOYI.md` §四.3，此处细化到本设计）

| 它的做法 | 为什么不抄 |
|---|---|
| `webSecurity=no` / `allowRunningInsecureContent=true` | 为注入让路放宽安全检查，我们是自建 UI + 结构化数据，没有这个必要 |
| 直接读页面 localStorage 当身份源 | 密钥以 base64 明文命名；我们的身份源应是自己的存储 |
| 注入改对方 DOM、500ms 定时器压制对方侧栏 | 寄人篱下的补丁，我们没有宿主 |
| 一号一 IP / 指纹隔离 / 代理链 | 已有结论：少数几个号自用，不需要 |
| 发送前**弹窗**确认 | 目标（先看译文再发）要抄；形态（打断式弹窗）不要——改输入区常驻预览 |
| 译文颜色/背景可配 | 过度装修；我们主气泡即中文，无需视觉区分 |
| 「端到端加密」与"必须解密才能翻译"并存的宣传 | 自相矛盾的话术（`REF-TUOYI.md` 已记） |
