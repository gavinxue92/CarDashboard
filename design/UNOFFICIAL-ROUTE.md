# 非官方路线的落地方案

> 状态：**已由用户决定**（2026-10-12 第 14 轮）。本文档只描述「怎么建」，不再重复「要不要走」。
> 相关的风险与代价在第一章一次性列明，之后不再反复劝阻。

## 一、决定记录

**决定：WhatsApp 接入走非官方路线**（linked-device 多设备协议族），放弃此前推荐的官方 Cloud API + Coexistence。

用户已知悉并接受的代价：

| # | 代价 | 说明 |
|---|---|---|
| 1 | **违反 WhatsApp ToS** | 驱动的是消费者端 App 协议，属自动化使用 |
| 2 | **封号作用于号码本身** | 换工具救不回已被标记的号；申诉极难；**阈值不可预测**（有用户只发几条即被封，有人长期无恙） |
| 3 | **产品不可对外销售** | 若将来卖给同行车商，客户号被封是信誉毁灭。届时必须迁回官方路线（见第五章） |
| 4 | **供应链风险** | 需自行校验依赖来源（Baileys 曾出现投毒 npm 分叉包 `lotusbail`，窃取 auth token） |

**定性依据（供日后复核）**：旧版 Pittcar 与竞品 SkySCRM 都出现「扫码登录」——
二维码只属于多设备协议握手，官方 Cloud API 没有这个流程。用户要的正是这一形态。

## 二、技术选型

两个候选，选一个作为**默认实现**，但**通道层必须接口化**，将来可换、可并存：

| 维度 | Baileys | whatsapp-web.js |
|---|---|---|
| 原理 | 直接用 WebSocket 实现多设备协议，**不需要浏览器** | 用 Puppeteer 驱动 headless Chromium 打开网页版 |
| 资源占用 | 每会话约 50MB，亚秒启动 | 每会话约 400–500MB |
| 数据获取 | 结构化、全量（协议层消息对象） | 结构化（也能爬 DOM） |
| 媒体处理 | 需自行处理加解密与下载 | 由浏览器侧完成 |
| 稳定性弱点 | 协议变更即失效，需跟进上游 | 网页版 DOM/行为变更即失效 |
| 依赖风险 | 生态分叉多，**必须锁定版本 + 校验 lock 完整性** | 依赖 Chromium 体积 |

**默认选择：Baileys**。理由是本项目规模小（少数几个号）、自用、追求资源效率和快速启动，
且**消息需要全量结构化入库**（后面要喂给业务模块），协议层比 DOM 层更干净。
`whatsapp-web.js` 作为备选实现保留在同一接口下。

**重要**：无论选哪个，`ChannelAdapter` 接口是稳定的（见第三章），业务代码不感知底层库。

### 通道适配器契约（**这份接口就是「预留的缝」**）

```ts
/** 一条规范化后的消息——无论底层是哪个库，业务层只认这个形状 */
interface NormalizedMessage {
  channelId: string;          // 账号标识（一个业务员一个号）
  chatId: string;             // WhatsApp 会话 JID，群组与 1:1 共用
  chatType: 'direct' | 'group';
  messageId: string;          // 通道侧消息 ID，用于幂等
  direction: 'inbound' | 'outbound';
  /** 消息来源：区分「本系统发出」与「业务员在手机上手打」 */
  origin: 'system' | 'phone';
  senderId: string;
  text: string | null;        // 原文，永不丢弃
  media: MediaRef[] | null;   // 媒体引用（不内联二进制）
  timestamp: number;
  replyToMessageId?: string;
}

interface ChannelAdapter {
  /** 扫码登录：产出二维码（字符串 payload）供前端渲染 */
  startLogin(channelId: string): Promise<{ qr: string; pairingCode?: string }>;
  /** 登录状态：已登录 / 待扫码 / 断开 */
  getStatus(channelId: string): Promise<'connected' | 'pending' | 'disconnected'>;
  /** 发文本（译文由上层传入，通道不做翻译） */
  sendText(channelId: string, chatId: string, text: string): Promise<{ messageId: string }>;
  /** 发媒体 */
  sendMedia(channelId: string, chatId: string, media: MediaRef, caption?: string): Promise<{ messageId: string }>;
  /** 拉取历史消息（用于首次接入后回填） */
  fetchHistory(channelId: string, chatId: string, limit?: number): Promise<NormalizedMessage[]>;
  /** 订阅入站事件 */
  onMessage(handler: (msg: NormalizedMessage) => void): void;
  /** 登出并清理本地凭证 */
  logout(channelId: string): Promise<void>;
}
```

三条必须守住的性质：

1. **`origin` 字段必须在第一天就有。** 它区分「本系统发出」与「业务员在手机上手打」——
   后者不经过翻译层，是已知的产品缺口，必须可观测、可统计。
2. **凭证（auth state）按 `channelId` 分目录持久化**，且在**数据库里记录归属**。
   这样「加一个业务员 = 加一份凭证 + 插一行数据」，不需要改代码发版。
3. **`text` 存原文，译文另存一列。** 与 `DESIGN.md` 的原则一致，不合并。

### 消息管道

| 方向 | 链路 |
|---|---|
| **入站** | 协议事件 → 规范化 → **先落库原文** → 判定语言 → 异步翻译 → 回填译文 → 推送界面 |
| **出站** | 业务员写中文 → 翻译 → **先把原文+译文一起落库** → 经适配器发出 → 回填通道 messageId |

纪律沿用第 12 轮确立的四条：**原文必留**、**翻译可失败但消息不能丢**、**接口化**、**缓存**。
出站额外一条：**消息发出不可撤回**，界面必须提供「先看译文再发」，不能静默直发。

## 四、相对官方路线，这条路多拿到了什么

| 能力 | 官方 Cloud API | 非官方路线 |
|---|---|---|
| 扫码登录 | ✗ 无此流程 | ✓ |
| **群组消息** | ✗ 收不到（共存模式也不支持） | ✓ **可恢复旧版被删掉的「群组」筛选 tab** |
| 主动发消息 | 受 24 小时窗口 + 模板审核限制 | ✓ 随时可发，无模板 |
| 按条计费 | ✓ 有（营销费率为 utility 的 2–9 倍） | ✗ **无按条费用** |
| 手机端 | 需 Coexistence 才能保留，且功能被砍 | ✓ 完整保留，且双向同步 |
| 历史消息 | 受限（媒体仅 14 天） | ✓ 可拉取历史与联系人 |
| 封号风险 | 无 | **有，且作用于号码** |
| 可转卖 | ✓ | **✗** |

**两个即刻可用的改动**：

1. `design/prototype.html` 里被删掉的**「群组」筛选 tab 可以加回来**（当前筛选为 全部 / 未读 / 窗口已关）。
2. **24 小时窗口提示**在非官方路线下**不再是硬约束**（可随时发），但建议**保留显示**——
   它仍是有用的「客户多久没回」的参考信息，只是文案从「需模板触达」改为「客户已 X 天未回」。

## 五、风险控制：使用纪律（不是「反检测工程」）

**明确的范围决定**：SkySCRM 那套「一号一 IP / 指纹画布隔离 / 模拟真人防封」基础设施，
是**为一个人管几十个号**设计的。本项目是少数几个号、深聊场景，**不建这套东西**——
它带来的复杂度远大于收益。

真正有效的是使用纪律：

| 纪律 | 具体做法 |
|---|---|
| **不做大规模群发** | 这是最容易被举报、最容易触发限流的动作。群发只对**明确同意的客户**、小批量、低频次 |
| **不做高频加好友 / 拉群** | 典型的批量营销特征 |
| **新号不立即高强度使用** | 接入后先按正常节奏使用一段时间 |
| **先用备用号试跑** | 稳定后再把主力号接进来 |
| **控制单号业务量** | 一个号对应一个业务员，不合并承载 |
| **依赖供应链** | 锁定确切版本，提交 `package-lock.json`，只从官方 registry 安装，警惕名称相近的分叉包 |

**迁移预案（必须现在就知道）**：若将来要对外销售，或某个号被标记，**唯一的出路是迁回官方路线**。
因此第三章的 `ChannelAdapter` 接口**必须包含 `CloudApiAdapter` 的位置**——
不是为了现在实现，而是为了那时「换一个适配器」而不是「重写业务」。

## 六、分阶段实施计划

每个阶段独立可验收，遵守 `AGENTS.md`：**代码 + 测试 + 提交**三者齐备。

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P0 · 骨架与契约** | 项目骨架 + 测试框架；`ChannelAdapter` 接口与 `NormalizedMessage` 定义；`MockAdapter`（假数据实现） | 接口有类型定义；MockAdapter 能产出消息；测试全绿 |
| **P1 · 存储与管道** | `Repository` 接口 + 内存实现 + SQLite 实现；入站/出站管道；幂等（按 `messageId`）| 契约测试对两种实现同样通过；重复消息不重复落库 |
| **P2 · 翻译层** | `Translator` 接口 + 一个实现 + 术语表占位符规则 + 缓存 | 同语言跳过；术语替换与还原正确；翻译失败不影响落库 |
| **P3 · 真实通道** | `BaileysAdapter`：扫码登录、收发文本、状态持久化 | 用备用号完成一次真实扫码 → 收 → 发；凭证重启后仍有效 |
| **P4 · 界面接通** | 把 `prototype.html` 的形态接上真实数据（会话列表、原文/译文、发送） | 端到端：客户发消息 → 界面显示译文 → 中文回复 → 客户收到 |
| **P5 · 扩展** | 群组 tab 恢复、媒体收发、历史回填、`origin: 'phone'` 的可视化 | 按需排期 |

**开始 P0 需要用户明确点头**——此前用户曾要求整体清除已搭的代码骨架，
