# 套壳路线实施方案（Electron + 官方网页版 + 注入扩展）

> **状态**：已由用户决定（2026-10-13）。用户原话：「我需要套壳，套壳后再进行扩展」。
> **与既有文档的关系**：本文档**取代** `UNOFFICIAL-ROUTE.md` §二 的「默认选择 Baileys」，成为非官方路线的**默认载体**；
> Baileys 降为同一接口下的备选实现，`ChannelAdapter` 契约本身**不变**（见 §四）。
> **参照对象**：拓译翻译客户端。其实现证据见 `REF-TUOYI.md`（18 平台清单、AES 注入、两层 RPC）。
> **上限**：本路线只在自家 `<webview>` 边界内工作，**不注入任何已安装的原生聊天客户端**（拓译同样如此，已实证 0 命中 Win32 窗口 API）。

---

## 一、决定记录

**决定：非官方路线的载体改为 Electron 套壳官方网页版。** 配套三项决策同轮拍板：

| # | 决策点 | 结论 | 影响 |
|---|---|---|---|
| 1 | 对话区归属 | **官方网页版占满对话区 + 周边自绘** | 形态即拓译的「两栏半 + 全包围」；我们此前设计的自绘对话区作废 |
| 2 | 消息与翻译通路 | **一期只做观测同步**（消息进我们的库、会话列表吃真数据），翻译与注入落**二期** | 一期业务员看到的是英文原文，翻译二期补 |
| 3 | 出站保护 | **拦截发送动作 → 我们的确认层 → 放行/改写** | 方向已定，随翻译一起落**二期**（一期无译文可确认，不建空壳） |

**一期的产品价值要说清**（否则会被误解为"退步"）：一期交付的是**工作台聚合**——在一个窗口里同时管多个号、
会话列表与客户档案吃自己的库、待跟进时长可统计。翻译是二期，不是不做。

## 二、取舍账

### 2.1 白拿的（原本都要自己实现）

| 能力 | 官方网页版提供 |
|---|---|
| 媒体渲染 | 图片 / 语音 / 视频 / 文件 / 贴纸，含内联播放与下载 |
| 送达与已读回执 | 原生（含勾号状态机） |
| 撤回 | 原生（含「对方已撤回」占位） |
| 群组 | 成员列表、@ 提及、群头像、群公告 |
| 历史与联系人 | linked device 天然双向同步，可拉全量 |
| 扫码登录 | 与手机端一致的「已登录设备」流程 |

### 2.2 代价（已知悉，不再反复劝阻）

| 代价 | 说明 |
|---|---|
| **DOM 依赖** | 注入层随对方网页改版失效，需长期维护。拓译 `webview.json` 带版本号 `5.2.57` 就是证据 |
| **资源** | 每账号约 400–500MB（对照 Baileys 约 50MB）。少数几个号自用可接受 |
| **输入面不受控** | 输入框在别人页面里，插入与拦截都要跨边界（§5.3 / §5.2） |
| **缺口依旧** | 业务员在**手机**上手打的消息仍绕过翻译层。套壳不改变这一点，只能把 `origin=phone` 显性化 |
| ToS / 封号 | 同 `UNOFFICIAL-ROUTE.md` §一，结论不变 |

### 2.3 ⚠️ 被这条路**推翻**的既有设计

`CONVERSATION-MODE.md` §三 C 原定：**「发送前确认不抄弹窗，改输入区常驻预览」**（理由是弹窗打断节奏）。

**该结论在套壳下不成立**：输入框属于官方网页版，我们无法"在它的输入框下方常驻"任何东西。
→ 只剩一条路：**拦截发送动作 → 出我们的覆盖层**。形态**接近**拓译的 `translationConfirmDialog`，
但我们的覆盖层里：译文可就地编辑、术语命中可点、取消后草稿保留（拓译的弹窗没有后两项）。

这是路线变更带来的**被动取舍**，不是重新评估后的偏好。已在 `CONVERSATION-MODE.md` §三 C 同步标注。

## 三、总体架构：三圈扩展

```
┌─ Electron 应用 ────────────────────────────────────────────────────────┐
│  主进程                                                                 │
│    我们的后端管道（复用现有 server/）: ingest → 抽字段 → 翻译 → 落库      │
│    账号管理（一号一 partition）· 注入层事件汇聚 · IPC                    │
└───────────────┬────────────────────────────────┬───────────────────────┘
                │ IPC                            │ IPC
┌───────────────┴──────────────┐  ┌──────────────┴───────────────────────┐
│ 外圈 · 自绘工作台（我们的）    │  │ 官方网页版 <webview>（别人的）         │
│   · 账号栏 / 会话列表         │  │  圈一 · preload（隔离世界）            │
│   · 客户工作区（常驻右栏）     │◄─┤   观察 DOM · 拦截出站 · 打标插副行     │
│   · 快捷插入栏（原创资产）     │  │   代写输入框（插入 ≠ 发送）            │
│   · 出站确认层（覆盖层）       │  │  圈二 · 页面主世界（按需才注入）        │
│                               │  │   调页面内部接口取结构化数据            │
│  数据源：我们自己的 Repository │  │  本体：媒体 / 回执 / 撤回 / 群组 免费   │
└───────────────────────────────┘  └──────────────────────────────────────┘
        事件与命令（新消息 · 已读 · 会话切换 ↔ 切会话 · 代写输入）
```

### 三条纪律（按"下沉一层，可维护性降一档"排序）

| 圈 | 位置 | 能做什么 | 成本 |
|---|---|---|---|
| **外圈** | 渲染进程，我们的代码 | 导航、会话列表、客户工作区、快捷插入栏、确认层 | 低，完全可控 |
| **圈一** | `<webview>` 的 **preload（隔离世界）** | 观察 DOM 变动、拦截出站、给消息节点打标 / 插副行、代写输入框 | 中，绑定对方 DOM 结构 |
| **圈二** | `<webview>` 的**页面主世界** | 调页面内部接口取结构化数据（联系人 / 会话桶 / 历史） | 高，全靠对方内部实现稳定 |

> **纪律：能在外圈做的，绝不下沉圈一；能在圈一做的，绝不下沉圈二。**
> 拓译三圈全用（且圈二靠运行时 AES 解密注入），我们**尽量只做外圈 + 圈一**。

### 载体的技术选型：`<webview>` 还是 `WebContentsView`

**结论：用 `<webview>`（`webPreferences.webviewTag: true`）。** 理由不是习惯，是硬约束：

| | `<webview>` | `WebContentsView` |
|---|---|---|
| 布局 | DOM 元素，随 flex 自动伸缩，四栏可拖 | 原生视图，**须主进程手动 `setBounds`**，每次拖拽都要同步 |
| 覆盖层 | z-index 正常，我们的确认层可覆盖对话区 | 原生视图**盖在 DOM 之上**，确认层会被压住，只能先隐藏它 |
| 预加载隔离 | `preload` 属性 | 支持，但需主进程维护 |

→ **「出站确认层必须覆盖对话区」这一条直接排除了 `WebContentsView`。**
拓译的产物里出现 `webviewTag` 字符串，与本文档结论一致。
若将来 Electron 移除 `webview`，迁移目标是 `WebContentsView` + 覆盖时临时缩退 bounds。

## 四、通道契约：不新增接口，只新增实现

`ChannelAdapter` 与 `NormalizedMessage` **一字不改**（定义见 `UNOFFICIAL-ROUTE.md` §三）。
新增一个实现，并把既有实现降级：

| 实现 | 事件来源 | 定位 |
|---|---|---|
| `MockAdapter` | 假数据 | 测试用（已存在） |
| **`WebviewBridgeAdapter`** | 注入层 `postMessage` | **默认实现**（本文档的落点） |
| `BaileysAdapter` | 协议 WebSocket | **降为备选**：资源省、无 DOM 依赖，但协议变更风险自担 |
| `CloudApiAdapter` | 官方 HTTP | 位置保留（对外销售时的迁移预案） |

**接口不变的意义**：通道契约测试（`channel/testing/contract.ts`）可直接复用——`WebviewBridgeAdapter` 接同一套用例即可。
这正是当初"通道层必须接口化"的回报。

### 四个字段在套壳下的新语义

| 字段 | 套壳下怎么取值 | 为什么关键 |
|---|---|---|
| `messageId` | 优先取对方 DOM 上的消息 ID（`data-id` / `id` 属性）；取不到则用 `chatId + 时间戳 + 正文哈希`兜底 | **幂等键**，见下方警告 |
| `origin` | 由注入层判断：观察到的节点是"我们发出的"还是"手机端同步过来的" | 决定是否显示「手机端 · 未经翻译」标记 |
| `chatType` | 由 URL / 头部是否含成员数判断 | 群组 tab 与对话区形态的前提 |
| `timestamp` | 优先取节点上的 `data-pre-plain-text` 一类属性，取不到用观察时刻 | 待跟进时长依赖它 |

> ⚠️ **幂等是套壳路线的头号风险。** DOM 观察会**重复看到**同一条消息：滚动、重渲染、会话来回切换都会重放。
> `Repository` 的按 `messageId` 幂等（P1 已实现）在这里**必须真正被用上**，且要有专门的重复投递测试。
> 这是本路线与 Baileys 最大的行为差异：协议层天然去重，DOM 层不会。

## 五、注入层契约（本项目自定）

### 5.1 选择器契约：集中成声明式配置，带版本号

**纪律：选择器不散落在逻辑里。** 一份 `selectors.ts`，按平台分区：

```ts
interface PlatformSelectors {
  platform: string;          // 'whatsapp'
  testedAgainst: string;     // 适配时对方网页版版本，如 '5.2.57'
  chatList: string;          // 会话列表容器
  chatItem: { root: string; name: string; lastMsg: string; unread: string };
  messageList: string;
  message: { root: string; idAttr: string; inbound: string; outbound: string; text: string; time: string };
  composer: string;          // 输入框（新版 WhatsApp 是 Lexical contenteditable）
  sendButton: string;
}
```

**版本号是运维信号，不是装饰**：对方改版 → 命中率下降 → 界面顶部提示「适配可能失效，请检查选择器」。

**配套自检（S5）**：进会话时跑几条选择器断言，失败即**显性告警**。
**绝不静默失败**——静默失败会让"注入没生效"表现为"功能没做"，排查成本极高。

### 5.2 出站拦截（二期）

```
业务员在网页版输入框写中文 → 点发送
  → 圈一拦截（capture 阶段 preventDefault，不触达真实发送）
  → 取输入框文本 → 送我们的管道 → 翻译 + 术语占位符保护
  → 出确认层（外圈 UI）：标出译文、可就地改、术语可点、取消则草稿保留
  → 业务员确认 → 代写回输入框 → 触发真实发送
  → 落库三份：原文 / 译文 / 实际发出文本
```

三条纪律：

1. **确认层是唯一出口。** 任何路径（含快捷插入、粘贴、回车键）都不能绕过。
2. **落库三份，不是两份。** 业务员改过译文的话，**以实际发出的文本为准**——否则日后对账对不上。
   这是对既有原则「原文与译文分列存储、永不合并」的补充，不是替代。
3. **拦截失败必须提示。** 选择器失效时不能退化为"静默直发"——那正是我们要防的事。

### 5.3 快捷插入栏（我们自己的，不受套壳影响）

插入 = **写进网页版输入框成为草稿**，不是发送。

- 复用同一套「代写输入框」原语：`contenteditable` 需**逐字派发 input 事件**，
  **禁止直接改 `innerHTML`**（会让对方框架的内部状态不同步，表现为"看着有字、点发送是空的"）
- 纪律不变：**插入 ≠ 发送**（`CONVERSATION-MODE.md` §三 D）
- 好处：常驻插入栏在外圈，我们完全控制——这正是它作为**原创资产**的价值

### 5.4 会话列表：不从 DOM 爬，走我们自己的库

| 方案 | 做法 | 判定 |
|---|---|---|
| 爬 DOM 渲染列表 | 观察会话列表 DOM 逐项同步 | ✗ 脆弱、丢字段、未滚动到的项加载不到 |
| **观测事件 + 自己的库** | 列表渲染自**我们的 Repository**；注入层只推**事件**（新消息 / 已读 / 会话切换 / 未读数） | ✓ **采用** |

→ 这解释了为什么「自绘会话列表」在套壳下**依然是对的**：列表不依赖对方 DOM 的渲染时序。
**唯一例外**：会话的**排序**直接照抄对方顺序（我们只落库，不自己算排序），避免与用户手上的手机端不一致。

## 六、分期实施

遵守 `AGENTS.md`：每阶段 **代码 + 测试 + 提交** 三者齐备。

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **S0 · 壳与登录** | Electron 壳；`<webview>` 载入 `web.whatsapp.com`；一号一 `partition`；扫码登录态持久化 | 用**备用号**扫码成功；重启后登录态仍在；两号并行互不串号 |
| **S1 · 观测同步** | 圈一观察新消息 → 推管道 → 落库；自绘会话列表吃真数据 | 手机端发一条 → 列表出现且摘要正确；**同一条重复观察不重复落库** |
| **S2 · 外圈补齐** | 客户工作区、快捷插入栏（写进网页版输入框）、账号筛选、待跟进时长 | 点话术 → 进输入框成草稿，**不自动发出** |
| **S3 · 翻译与注入** | 入站译文副行注入；术语命中可点；同语种跳过 | 客户发英文 → 副行出现中文；同语种客户不出现副行 |
| **S4 · 出站拦截** | 拦发送 → 确认层 → 落库三份 → 放行 | 写中文点发送 → 出确认层 → 确认后客户收到英文；**取消则输入框文本保留** |
| **S5 · 失效告警** | 选择器自检 + 版本号 + 失效显性告警 | 人为改坏一个选择器 → 界面告警，而非静默失效 |

⚠️ **S0–S1 的验收必须由用户拿备用号真扫码完成**，我无法单独完成。
这是与既有 P3 完全相同的一条限制（见 `UNOFFICIAL-ROUTE.md` §六）。

**一期 = S0 + S1 + S2**（用户决策 2：翻译与注入落二期）。S3–S5 即二期。

## 七、不抄清单（针对套壳路线）

| 拓译的做法 | 为什么不抄 |
|---|---|
| `webSecurity=no` / `allowRunningInsecureContent=true` | 为注入放宽安全边界。我们只在 preload 隔离世界观察，**不开这个口子** |
| 直接读页面 `localStorage` 当身份源 | 它的密钥以 base64 明文命名；我们的身份源是自己 的库 |
| 运行时 AES 解密 `index.enc` 再注入主世界 | 加密注入是**圈二**的必要手段（拓译 563KB 的 `index.enc`）。我们**优先只做圈一**，能不下沉就不下沉 |
| 500ms 定时器反复压制对方侧栏 | 寄人篱下的补丁。我们不动对方的 UI（不动 = 改版后少一处会坏） |
| 一切功能走弹窗（快捷消息 / 推荐回复 / 客户档案） | 它用弹窗是因为对话区是别人的页面；我们的插入栏、客户档案都在**外圈**，常驻即可 |
| 一号一 IP / 指纹隔离 / 代理链 | 既有结论：少数几个号自用不需要那套基础设施 |
