## 0. 范围声明（先读这一条）

**本方案只实现需求规格说明书中已确认的 34 条 FR，不新增任何未被需求覆盖的功能。**

一条能力是否进入本版，用两个条件同时判定：

1. 有 FR 编号支撑；
2. **本版有界面或链路承载它**。

不同时满足的，一律不进本版。据此明确排除：

| 排除项                        | 原因                                   |
| -------------------------- | ------------------------------------ |
| **工作台登录页与账号体系**            | FR-2.1~2.4 整组推迟（需求文档 4.3）；本版启动直接进主界面 |
| **服务端与数据库**                | 无登录层即无服务端调用方；本版为独立单机应用               |
| **自动更新（FR-1.6）**           | 无服务端静态分发即无更新源，本版推迟                   |
| 多租户 / 组织架构                 | 34 条 FR 中无任何条目要求，且与「单企业内部使用」口径矛盾     |
| RBAC 角色权限体系                | 客户端只有一种角色，无权限界面可承载                   |
| 审计日志中心                     | 无 FR 支撑，无查询界面                        |
| Redis / 对象存储 / 灰度发布 / 监控看板 | 无 FR 支撑；本版无服务端                       |
| 消息网关与消息入库                  | 属 V2 通信内核升级（需求文档第 9 节已登记），非本版事项      |
| Sentry 等第三方监控服务            | 崩溃与运行日志先写客户端本地文件，够用                  |

## 2. 总体架构

本版没有服务端，只有一个进程边界：**主进程 ↔ 渲染进程**。

```
┌──────────────────────── 客户端 · Electron 单机（Windows） ────────────────────────┐
│                                                                                 │
│   主进程 (main)                          渲染进程 (renderer · Vue 3)                │
│   ├─ 窗口与内嵌视图生命周期                   ├─ 工作台框架（标题栏 / 左侧导航 / 内容区）    │
│   ├─ session 分区创建 / 清除                ├─ WhatsApp 模块容器（加载 / 内嵌 / 故障覆盖）│
│   ├─ UA 覆写 · 按分区设代理（可选）             ├─ 右侧功能栏 + 翻译设置弹窗（壳）           │
│   ├─ IPC 通道                             └─ 状态圆点 / 账号备注 / ⋯ 菜单 / Toast    │
│   └─ 本地日志                                                                │
│         │                                     ▲                                │
│         │ preload (contextBridge 最小 API)      │                                │
│         └─────────────────────────────────────┘                                │
│                    │                          │                                │
│          session 分区（登录态）             内嵌视图（官方页面）                        │
│         persist:wa-<分区标识>                     │                              │
│         ↑ 分区标识由一处常量注入，                  │                              │
│           加入登录层后改为用户标识                   │                              │
└────────────────────────┼──────────────────────────┼────────────────────────────┘
                         │                          │ 官方自有连接（我方零参与）
                    （本版无）                       ▼
                                          ┌──────────────────────────────┐
                                          │ WhatsApp 官方服务（境外）           │
                                          │  二维码 · 消息 · 账号状态全部在此      │
                                          └──────────────────────────────┘
```

两条链路：

| 链路  | 走向                   | 我方参与度       |
| --- | -------------------- | ----------- |
| 消息面 | 内嵌视图 ↔ WhatsApp 官方服务 | **零参与、零记录** |
| 控制面 | **本版不存在**（无登录、无服务端）  | —           |

> 服务端是 V1.1 的事：届时只需新增登录接口与静态分发（安装包 + 更新清单），**本版架构图的左侧全部保持不动**。

## 3. WhatsApp 接入方案（问题 1）

### 3.1 方案选择

**在客户端内嵌官方 WhatsApp Web 页面**，不注入脚本、不改写 DOM、不自动化操作。

理由：`web.whatsapp.com` 响应头含 `frame-ancestors 'none'`，任何网页都无法以 iframe 嵌入——这是 V1 必须做桌面客户端的直接原因；而内嵌官方页面是唯一能拿到"全功能、原生体验、最低封号风险"的路径。

### 3.2 登录绑定流程

| 步骤 | 销售看到                         | 系统行为                                                           |
| -- | ---------------------------- | -------------------------------------------------------------- |
| 1  | 点左侧「沟通 → WhatsApp」           | 主进程创建内嵌视图，绑定独立分区 `persist:wa-<分区标识>`                           |
| 2  | 内容区显示「正在打开 WhatsApp…」，导航圆点转黄 | 加载 `https://web.whatsapp.com`，UA 覆写为常规 Chrome；网络不可达时该分区单独走代理出口 |
| 3  | 官方页面呈现「关联设备」二维码与倒计时          | 我方只监听加载事件，不碰页面 DOM（FR-3.4）                                     |
| 4  | 手机 WhatsApp →「已关联的设备」→ 扫码确认  | 配对全过程在官方页面内完成，我方不感知（FR-3.5 / 3.6 转验收项）                         |
| 5  | 官方页面切换到聊天界面                  | 凭证落盘到该分区并持久化 → 重启、切走再切回都免扫码（FR-3.3 / 3.9）                      |

登录态生命周期（FR-3.9~3.11）：

| 项   | 做法                                                                                  |
| --- | ----------------------------------------------------------------------------------- |
| 持久化 | `session.fromPartition('persist:wa-<分区标识>')`，由 Electron 写入磁盘                        |
| 隔离  | **本版**：分区标识为固定常量，隔离由 Windows 用户目录承担（FR-3.10 口径已修正）；**加入登录层后**：分区标识改为用户 ID，实现 FR-4.2 |
| 加密  | 由操作系统用户目录权限 + Electron 分区机制承载，不做额外自定义加密（FR-3.11 标「中」）                               |
| 清除  | 解绑时 `clearStorageData()` 清空该分区，回到加载态重新扫码（FR-3.17 / 3.18）；卸载时随应用数据一并清除（FR-1.7）       |

> ⚠️ **分区标识必须做成单一注入点，这是本方案唯一不能省的预防性设计。** 本版传入固定值；将来加入登录层时改为用户 ID 即可，代码结构不变。若本版把分区名写死、后续又沿用同名分区，会出现「任何人登录后都能看到同一个已绑定的号」的串号问题——那正是 FR-4.2 要防的事。

### 3.3 消息收发流程

| 方向 | 路径                                             | 我方参与 |
| -- | ---------------------------------------------- | ---- |
| 发送 | 销售在内嵌官方页面输入并发送 → 页面自身的 WebSocket → WhatsApp 服务 | 0    |
| 接收 | WhatsApp 服务 → 页面长连接推送 → 页面自行渲染                 | 0    |
| 落库 | 无                                              | 0    |

**这是方案 A 的固有边界，不是缺陷。** 其后果已在需求文档第 6.2 节记录：后续「获客管线」「CRM 任务」不能建立在 WhatsApp 对话之上，需等 V2 升级通信内核。

### 3.4 我方唯一能观测到的事件（对应 FR-3.12）

| 事件                                                       | 映射状态          |
| -------------------------------------------------------- | ------------- |
| `did-start-loading`                                      | 加载中（黄）        |
| `did-finish-load`                                        | 运行中（绿）        |
| `did-fail-load` / `render-process-gone` / `unresponsive` | 连接异常（红）＋ 顶部浮条 |

状态语义**只能是「页面运行状态」**，悬停必须提示「不代表账号在线」。手机端解除关联时我方感知不到，圆点仍为绿色，官方页面会自行跳回二维码页。

### 3.5 关键实现要点

| 要点     | 做法                                                                                                      |
| ------ | ------------------------------------------------------------------------------------------------------- |
| 承载方式   | `WebContentsView`（Electron 44 推荐）承载官方页面，置于我方布局预留的内容区                                                    |
| UA 覆写  | 该分区 `setUserAgent` 为常规 Chrome 标识，避免被判定为不受支持的客户端                                                         |
| 代理（可选） | `session.setProxy()` 只作用于 WA 分区，用于办公网络不可达的情况（费用另计）                                                      |
| 常驻后台   | 切换导航不销毁视图，返回直接恢复（已确认）；代价是常驻内存约 300~500 MB                                                               |
| 加载超时   | 10 秒后改为「仍在加载，网络可能较慢…」并露出重试按钮（FR-3.8）                                                                    |
| 安全基线   | `contextIsolation: true`、`nodeIntegration: false`、`sandbox: true`、严格 CSP、IPC 参数校验、导航与 `window.open` 白名单 |
| 页面空白兜底 | 故障覆盖层始终给出下一步动作，绝不白屏（FR-3.14）                                                                            |

### 3.6 不可实现项（沿用交互说明第 9 节，勿在验收中当作缺陷）

| 需求           | 处理                             |
| ------------ | ------------------------------ |
| FR-3.5 / 3.6 | 官方页面自带行为，转「验收确认项」              |
| FR-3.15      | 降为低：官方页面自身提示即为反馈，V1 不做自动检测与帮助页 |
| FR-3.16      | 移出 V1：无事件可订阅                   |
| FR-3.7       | 替代为「人工账号备注」，显示在左侧导航            |

## 4. 职责划分（问题 2）

### 4.1 客户端 · 渲染进程（我方 UI）

标题栏、左侧导航、导航状态圆点与账号备注、⋯ 菜单、右侧功能栏、翻译设置弹窗（壳）、解绑确认弹窗、Toast、故障覆盖层、占位页。

**不负责**：渲染聊天界面、渲染二维码、读写消息、账号信息读取。

### 4.2 客户端 · 主进程

窗口与内嵌视图生命周期、session 分区创建与清除、UA 覆写、按分区设代理、IPC 通道、本地日志落盘、导航白名单。

**不负责**：解析页面内容、注入脚本、抓取 DOM、自动更新（本版推迟，见 FR-1.6）。

### 4.3 preload

用 `contextBridge` 暴露最小 API，不暴露 `require`：

```
WhatsApp： wa.reload() / wa.onStatus(cb) / wa.unbind()
设置层：   memo.get() / memo.set(v)               ← 账号备注（FR-3.7）
        settings.get() / settings.save(cfg)      ← 翻译设置预留接口（FR-3.21）
```

> 原「工作台层 `auth.*`」已随登录层一并推迟，本版不暴露。

### 4.4 服务端（本版不建）

**本版服务端代码量为 0，不部署任何服务、不建数据库、不需要域名。**

| 项    | 本版  | V1.1 加入登录层时              |
| ---- | --- | ------------------------ |
| 后端进程 | 不建  | Node 24 + 登录接口（约一个路由文件）  |
| 数据库  | 不建  | Postgres，仅 `users` 一张表   |
| 静态分发 | 不建  | nginx `/dl` 目录，放安装包与更新清单 |
| 域名证书 | 不需要 | 一个域名 + Let's Encrypt 证书  |

> 消息中转、二维码生成、消息存储、配置中心、审计、多租户、权限体系——**永久不做**（见第 0 节排除清单）。

### 4.5 数据存储

**只有客户端一处，全部为本地文件。**

| 位置  | 技术                     | 存什么                                   |
| --- | ---------------------- | ------------------------------------- |
| 客户端 | `electron-store`（JSON） | 账号备注、翻译设置缓存、上次选中模块、重连日志               |
| 客户端 | Electron session 分区    | WhatsApp 登录态（由 Electron 自行管理，我方不读取内容） |

无服务端数据库、无消息表、无客户表。

### 4.6 接口契约

**本版无任何网络接口。** 两类契约仍然需要提前冻结定义，放在 `packages/shared`：

```
IPC 契约（主进程 ↔ 渲染进程）
  wa.reload()                     → void
  wa.onStatus(cb)                 → '运行中' | '加载中' | '连接异常'      ← FR-3.12
  wa.unbind()                     → void                            ← FR-3.17
  memo.get() / memo.set(v)        → string | void                    ← FR-3.7
  settings.get() / settings.save(cfg) / settings.reset() → 翻译设置      ← FR-3.21

翻译设置契约（字段冻结，只许换实现不许改结构）
  WATranslateSettings { ... }     ← 详见交互说明 7.4 节
```


> 契约冻结的意义：将来接入真实翻译渠道、或加入登录接口时，**只替换实现，不改调用方**。

### 4.7 IPC 通道集中定义

IPC 通道名与参数类型集中在 `packages/shared`，避免主进程与渲染进程字段对不上。

## 6. 部署（问题 4）

### 6.1 本版无需部署

本版是单机客户端，**没有服务端可部署**：

| 项    | 本版做法                                  |
| ---- | ------------------------------------- |
| 云服务器 | **不需要**。客户端不调用任何后端，你那台服务器本版先闲置          |
| 域名证书 | **不需要**                               |
| 数据库  | **不需要**                               |
| 分发方式 | `electron-builder` 本地打出 NSIS 安装包，直接拷给使用者 |
| 环境变量 | 仅构建期 `VITE_WA_PROXY`（可空）               |

> **消息收发是客户端直连 WhatsApp，从头到尾不经过任何我方服务器。** 所以"本版不用服务器"对 WhatsApp 能否使用毫无影响。真正决定可用性的是**销售办公网络能否访问境外**。

### 6.2 本版的"发布"流程

```
本地打包（electron-builder 出 NSIS 安装包）
  → 计算 SHA-256 校验和，附在交付说明里
  → 直接拷给使用者 / 放共享目录
  → 使用者双击安装，SmartScreen 告警时点「更多信息 → 仍要运行」
```

无版本检查、无自动更新（FR-1.6 推迟）。版本号靠文件名区分。

> 由于本版已确认**卸载即清除全部数据**（含 WhatsApp 登录态与账号备注），每次重装都要重新扫码一次。这一点需写进交付说明，避免使用者误以为是故障。

### 6.3 部署形态（属 V1.1，本版不实施）

将来加入登录层与自动更新时，你那台服务器上三个容器即可（`deploy/docker-compose.yml`）：

```
一台云服务器（2C2G 起）
├─ nginx     443/TLS 终止 · /api 反向代理 · /dl 静态目录
├─ api       Node 24，登录接口
└─ postgres  仅 users 表
```

⚠️ 届时若服务器在**中国大陆**，域名走 80/443 需 ICP 备案（1~3 周）；中国香港或境外机器免备案，最省事。现在不用管，但值得提前知道。

## 7. 技术选择：理由 / 成本 / 限制（问题 5）

| 选择                       | 理由                        | 成本（估算）                        | 限制                                         |
| ------------------------ | ------------------------- | ----------------------------- | ------------------------------------------ |
| **Electron 44**          | 唯一能内嵌官方页面的形态；一套代码兼顾将来浏览器端 | 免费；安装包 80~120 MB              | 内存 300~500 MB；Chromium 需持续跟进；无 32 位构建      |
| **内嵌官方页（不注入）**           | 全功能、原生体验、封号风险最低           | 无                             | 读不到消息、改不了样式；官方改版可能影响                       |
| **独立 session 分区（标识参数化）**  | 重启免扫码；标识留注入点，加入登录层时零改造    | 每分区几十 MB 磁盘                   | 解绑/卸载必须显式清分区，否则残留登录态                       |
| **UA 覆写为常规 Chrome**      | 避免被官方判为不受支持的客户端           | 无                             | 需跟随官方对浏览器版本的要求调整                           |
| **按分区设代理（可选）**           | 办公网络不通时唯一救法，只影响 WA 分区     | 代理服务 ¥50~200/月                | 增加一跳延迟；代理稳定性成为新故障点                         |
| **Vue 3 + Vite + TS**    | 体量小、构建快、Electron 生态成熟     | 免费                            | 本项目 UI 简单，与 React 的差距不构成影响                 |
| **electron-store**       | 零原生编译，开箱可用                | 免费                            | 数据量大后性能差，无查询能力（本项目只存几 KB，够用）               |
| **本版不建服务端**              | 无登录即无调用方，省掉整条运维链          | **¥0**（服务器本版闲置）               | 无法统一管理账号与下发版本；FR-1.6 一并推迟                  |
| **electron-updater**     | 官方生态标准方案                  | 免费                            | **本版推迟**（无更新源）；将来启用需 HTTPS + 稳定 feed 地址      |
| **不做代码签名**               | 已确认选择，省年费与核验周期            | ¥0                            | 首次安装有 SmartScreen 告警，需安装引导 + SHA-256 校验和补偿 |

**Electron 版本节奏（需写成纪律）**：官方只维护最近 3 个大版本，约 8 周出一个大版本。当前 44 为稳定线；45 于 2026-10-20 转稳定，同日 42 进入 EOL。建议约定：**大版本发布后 30 天内升级，绝不停在 EOL 线上**。

## 8. 目录结构（问题 6）

本版只有 `apps/desktop` 一个应用，**没有 `apps/server`、没有 `deploy/`**：

```
CarDashboard/
├─ docs/                          # 需求说明书 · 交互说明 · 本方案
├─ prototype/                     # 交互原型
├─ apps/
│  └─ desktop/                    # Electron 客户端（本版的全部）
│     ├─ src/main/                #   window.ts / embed-view.ts / session.ts
│     │                          #   partition.ts（分区标识单一注入点）· ipc.ts
│     │                          #   logger.ts / nav-guard.ts
│     ├─ src/preload/             #   contextBridge 最小 API
│     ├─ src/renderer/            #   我方 UI
│     │  ├─ layout/               #     标题栏 / 导航 / 内容区
│     │  ├─ views/                #     whatsapp/ · placeholders/（无 login/）
│     │  ├─ components/           #     状态圆点 / 账号备注 / ⋯菜单 / 功能栏
│     │  │                        #     翻译设置弹窗 / 解绑弹窗 / Toast / 故障覆盖层
│     │  ├─ stores/  styles/
│     │  └─ main.ts
│     ├─ electron-builder.yml
│     └─ .env.development / .env.production
├─ packages/
│  ├─ shared/                     # IPC 契约 + 翻译设置类型（单一来源）
│  └─ config/                     # tsconfig / eslint / 构建脚本
├─ .env.example
├─ pnpm-workspace.yaml
└─ README.md
```

> 保留 `pnpm-workspace.yaml` 与 `packages/` 两层，是因为服务端与共享契约将来要落进来——现在多一层目录，比将来动工程结构便宜。`partition.ts` 单列成文件，正是为了让"分区标识"只有一个可改动的地方。

## 9. 模拟数据 vs 真实服务（问题 7）

本版没有服务端，所以这张表比原方案短了一大截——**只剩一项必须真实**：

| 可以先本地造                            | 必须连真实                                 |
| --------------------------------- | ------------------------------------- |
| 账号备注、翻译设置读写（本就只存本地，无需造）           | **官方 WhatsApp Web 页面加载**：本版核心，无法 Mock，依赖境外可达 |
| 获客 / 业务 / 账号三域占位页（本就无数据）          | **手机扫码配对**：必须真实号码 + 真机，并验证 UA 覆写后官方不拒绝 |
| 三色状态、故障覆盖层、Toast（可用开发开关强制切换状态做联调） | 消息收发（完全在官方页面内，我方不参与）                  |
| 解绑 / 卸载清理（可在开发环境用临时分区验证）          | **常驻 8 小时稳定性**：只能真实挂机观察                 |

⚠️ 原型中的二维码是绘制的示意，只能用于评审；真实二维码由官方页面生成，验收必须真机扫。

**被砍掉的"模拟项"说明**：原方案里"本地假登录""本地静态 feed 跑通自动更新流程"两项，已随登录层与 FR-1.6 一并推迟——本版没有它们要模拟的对象。

## 10. 备选方案 B（协议库 + 自研聊天界面）

| 维度   | 方案 B 做法                                              |
| ---- | ---------------------------------------------------- |
| 接入   | 服务端运行 WhatsApp Web 多设备协议的 JS 实现（Baileys 这一类），不使用官方页面 |
| 登录   | 服务端请求配对二维码 → 前端渲染**我方自己的二维码** → 凭证加密存服务端             |
| 收发   | 客户端 → 我方 API/WebSocket → 协议库 → WhatsApp；媒体走存储；消息全量入库 |
| 前端   | 自研聊天界面（会话列表、消息流、发送框、媒体预览、已读态、输入态、搜索）                 |
| 新增服务 | 常驻消息网关（每号一连接/一进程）+ 消息库 + 媒体存储 + 推送通道                 |

**收益**：消息可入库检索，获客管线与 CRM 任务才真正成立；可做多号聚合；翻译可落地；出口网络我方可控。

**代价**：非官方实现存在**封号风险**；协议变更需跟随升级；每号常驻内存；聊天界面自研工作量约为方案 A 外壳的 **3~5 倍**。

**切换成本**：客户端只需替换通信层实现，外壳、导航、账号体系、设置弹窗全部复用——即需求文档登记的 V2 升级路径。

> 补充澄清：WhatsApp 现支持多设备关联，因此"内嵌官方页 + 协议库"同时在线理论可行，但两条链路会争抢同一账号状态、故障面与封号面均扩大，**不建议混用**；若将来要做，须先小范围灰度验证。

## 13. 待确认事项

1. **WhatsApp 号码来源**：公司统一采购还是销售自带，决定合规风险等级与备用号策略。**本版建议统一使用公司号码**，避免销售个人主号被限制。
2. **访问网络条件**：销售当前在什么网络环境下办公，是否有稳定的境外访问条件。**这是本版第一风险**（对应第 12 节第 1 项）。
3. **销售团队规模**：多少人使用，决定分发方式（多少台设备要安装）。
4. **样板车展厅的形态**：属业务域，本版不实现，但影响后续版本规划。

> 已确认（不再列为待定）：登录层不做、服务端不建、卸载即清除全部数据、办公网络与服务器备案的关系（本版无服务端，备案问题自动消解）。
